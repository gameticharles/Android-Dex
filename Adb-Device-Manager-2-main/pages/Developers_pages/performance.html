Improvement 1 — Boot Speed
⚡
JAR Hash Caching — Skip Redundant Pushes
Windows side · Dart · Boot flow (step 0.38)
High
Problem Every boot runs adb push to copy the Logic Engine JAR to /data/local/tmp/ on the device — even when the JAR hasn't changed. This is the single slowest step (3–10s on WiFi).
Solution Before pushing, run adb shell md5sum on the remote file and compare it to the local JAR's MD5. Only push if they differ. Cache the last-pushed hash in a local file to skip the remote check entirely on subsequent identical launches.

Implementation in Dart (Windows side, boot flow):

// boot_manager.dart

Future<bool> shouldPushJar(String localJarPath, String deviceJarPath) async {
  // 1. Hash the local JAR
  final localBytes = await File(localJarPath).readAsBytes();
  final localMd5 = md5.convert(localBytes).toString();

  // 2. Check cached hash from last push (no ADB call needed)
  final cacheFile = File('jar_hash.cache');
  if (await cacheFile.exists()) {
    final cachedHash = await cacheFile.readAsString();
    if (cachedHash.trim() == localMd5) return false; // skip push ✓
  }

  // 3. Fallback: check on-device hash via ADB
  final result = await runAdb(['shell', 'md5sum', deviceJarPath]);
  final deviceMd5 = result.stdout.split(' ').first.trim();

  if (deviceMd5 == localMd5) {
    await cacheFile.writeAsString(localMd5); // update cache
    return false;
  }
  return true; // JAR changed — push required
}

// In boot sequence:
if (await shouldPushJar(localPath, remotePath)) {
  await runAdb(['push', localPath, remotePath]);
  await cacheFile.writeAsString(localMd5);
}
The cache file should be invalidated if the app version changes. Tie it to the app's build number or the JAR file's modification timestamp.
Improvement 2 — Boot Speed
🚀
Parallel Boot Steps — Concurrent Package Check & JAR Push
Windows side · Dart · Boot flow (steps 0.38 & 0.55)
High
Problem The boot sequence is fully sequential: the app waits for adb push to finish before even checking if the companion APK is installed (pm list packages). These two operations are independent.
Solution Run the JAR push and APK package check concurrently using Future.wait(). Both results are needed before step 5 (am start), but they have no dependency on each other. 
// Current (sequential) — total time = pushTime + checkTime
await pushJarToDevice();           // ~5s on WiFi
await checkCompanionApkInstalled(); // ~1s
await startServerService();

// Improved (parallel) — total time = max(pushTime, checkTime)
final results = await Future.wait([
  pushJarIfNeeded(),           // ~5s (or 0s with hash cache)
  checkCompanionApkInstalled(), // ~1s, runs concurrently
]);
final apkInstalled = results[1] as bool;
if (!apkInstalled) await installCompanionApk();
await startServerService();
Improvement 3 — Data Loading
📋
Paginated REST Endpoints — Contacts, Calls & SMS
Android side · Kotlin · HTTP endpoints on port 4567
High
Problem GET /contacts/get_all, /call_settings/get_all_calls, and /sms_settings/get_all_sms return the entire dataset in a single response — including Base64 contact photos. A phone with 1,000 contacts can return several MB, blocking the UI until fully parsed.
Solution Add offset + limit query parameters. Return the first page immediately (fast first render), then fetch subsequent pages as the user scrolls. Separate photo loading from metadata loading.

Android side — update the Ktor/NanoHTTPD route handler:

// Kotlin — contacts endpoint (Android, port 4567)
get("/contacts/get_all") {
    val offset = call.request.queryParameters["offset"]?.toIntOrNull() ?: 0
    val limit  = call.request.queryParameters["limit"]?.toIntOrNull()  ?: 50
    val includePhotos = call.request.queryParameters["photos"] != "false"

    val contacts = contactRepo
        .getAll()
        .drop(offset)
        .take(limit)
        .map { c ->
            if (!includePhotos) c.copy(photoBase64 = null)
            else c
        }

    call.respond(mapOf(
        "status" to "success",
        "total"  to contactRepo.count(),
        "offset" to offset,
        "limit"  to limit,
        "contacts" to contacts
    ))
}

Windows side — fetch metadata first, then photos lazily:

// Dart — ContactsService
Future<void> loadContacts() async {
  // 1. Load first page without photos — instant first render
  final page1 = await fetchContacts(offset: 0, limit: 50, photos: false);
  setState(() => contacts = page1.contacts);

  // 2. Load remaining pages in background
  int offset = 50;
  while (offset < page1.total) {
    final page = await fetchContacts(offset: offset, limit: 50, photos: false);
    setState(() => contacts.addAll(page.contacts));
    offset += 50;
  }

  // 3. Lazy-load photos only for visible contacts
  loadPhotosForVisible(visibleRange);
}
Improvement 4 — Network Efficiency
🖼️
Binary Image Endpoints — Eliminate Base64 Overhead
Android side · Kotlin + Windows side · Dart
Medium
Problem Every image (wallpaper, contact photos, Google profile picture) is encoded as Base64 inside JSON responses. Base64 inflates binary size by ~33% and requires a CPU decode step on both sides on every transfer.
Solution Add dedicated binary endpoints that return image/jpeg directly. This removes the encode/decode overhead entirely and makes responses compatible with standard HTTP image caching. 
// Kotlin — new binary photo endpoint
get("/contacts/photo/{id}") {
    val contactId = call.parameters["id"]?.toLongOrNull()
        ?: return@get call.respond(HttpStatusCode.BadRequest)

    val photoBytes = contactRepo.getPhotoBytes(contactId)
        ?: return@get call.respond(HttpStatusCode.NotFound)

    call.respondBytes(photoBytes, ContentType.Image.JPEG)
    // No Base64. No JSON wrapper. Raw JPEG bytes.
}

// Similarly for wallpaper:
get("/device/wallpaper") {
    val bmp = WallpaperManager.getInstance(context).drawable
    val baos = ByteArrayOutputStream()
    (bmp as BitmapDrawable).bitmap.compress(Bitmap.CompressFormat.WEBP_LOSSY, 80, baos)
    call.respondBytes(baos.toByteArray(), ContentType("image", "webp"))
}
Use WEBP_LOSSY at quality 75–80 for wallpapers. WebP saves another 25–35% over JPEG with no perceptible quality loss.
Improvement 5 — Control Latency
⚡
JAR TCP Command Batching — Merge Rapid Commands
Windows side · Dart · AdbTcpServer / Logic Engine TCP
Medium
Problem Each command to the Logic Engine (JAR) — volume up, screen toggle, app launch — is a separate TCP round-trip over ADB. Rapid actions (e.g. holding a volume key) generate dozens of individual requests per second, each paying the full ADB tunnel latency cost.
Solution Buffer commands in a debounce queue on the Dart side. Flush as a batch every 16ms (one frame). The JAR processes them sequentially, but the network sees one packet instead of many. 
// Dart — command batcher
class JarCommandBatcher {
  final _queue = <Map<String, dynamic>>[];
  Timer? _flushTimer;

  void send(String command, [Map? params]) {
    _queue.add({'cmd': command, ...?params});
    _flushTimer ??= Timer(const Duration(milliseconds: 16), _flush);
  }

  void _flush() {
    if (_queue.isEmpty) return;
    // Send all queued commands as a single JSON array over TCP
    jarTcpSocket.write(jsonEncode({
      'type': 'batch',
      'commands': List.from(_queue),
    }));
    _queue.clear();
    _flushTimer = null;
  }
}
Improvement 6 — Memory Efficiency
🔗
Shared Call Manager Socket — Reduce Process Count
Windows side · Dart · Call Manager 1 architecture
Low
Problem Call Manager 1 spawns a new call_manager.exe child process for each connected device IP. With 3+ devices, this creates 3+ system-level processes, each holding their own sockets and memory. Windows process overhead is significant (~30MB+ per process).
Solution Run a single multiplexed call manager process. Route by device IP internally using a Map<String, CallSession>. Only the session lookup is per-IP — the socket server and process are shared. 
// Dart — single shared call manager with IP-keyed sessions
class SharedCallManager {
  final _sessions = <String, CallSession>{}; // keyed by device IP

  void onCallEvent(String deviceIp, Map event) {
    final session = _sessions.putIfAbsent(
      deviceIp,
      () => CallSession(ip: deviceIp),
    );
    session.handleEvent(event);
  }

  void onDeviceDisconnected(String deviceIp) {
    _sessions.remove(deviceIp)?.dispose();
  }
}
// One global instance instead of one process per device.
This is a larger refactor since call_manager.exe is a compiled separate binary. Consider this for a future major version; the other improvements are lower-risk and higher-yield.
